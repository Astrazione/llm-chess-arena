# Проверка этапа 3: веб-интерфейс и SSE

Дата: 15 ноября 2026 года. Среда: Windows, Docker Desktop/WSL2, Linux-контейнеры Node.js 24. Все установки зависимостей, линтеры, TypeScript, сборки и браузер выполнялись через Docker Compose. Локальные node_modules не создавались.

## Реализовано

- React/TypeScript, react-chessboard 5.12.1 с актуальным API `options`, тёмная адаптивная тема. На десктопе доска слева, управление/история/настройки справа; журнал в отдельной панели.
- Позиции только из backend FEN, SAN-история парами и навигация по готовым positions. Исторический просмотр сохраняет выбранную позицию при продолжающейся игре. Есть переворот доски, активный игрок, шах/мат, результат, подсветка последнего и распознаваемого ошибочного хода.
- Start/Pause/Resume/Next Move/Stop/Reset с доступностью по status/busy. Stop/Reset остаются доступны при ожидании модели. После Reset не отображаются история и события прежнего gameId.
- Настройки двух Mock Providers: стратегии, seed, сценарии UCI, задержка ответа, частота неверных ходов. Общие maxPlies/retries, server moveDelayMs, режим A/B, системная инструкция и автоматический/пошаговый запуск.
- Панели игроков: провайдер/модель/цвет/статус/ходы/ошибки/последнее время ответа. Общая статистика полуходов, ошибок и повторов. Журнал показывает запросы, ходы, retries, категории ошибок, модель, полуход, исходный ответ и диагностику.
- SSE `/api/matches/:id/stream`: versioned начальный snapshot, обновления `{event,snapshot}`, id=sequence, heartbeat 15 с, очистка подписок при disconnect/preClose, ограничение накопленного буфера медленного клиента. Снимки больше socket highWaterMark не вызывают разрыв сами по себе.
- Нативный EventSource reconnect, обработка offline/online, REST-восстановление snapshots и пагинированного журнала, дедупликация sequence, защита generation/gameId. Постоянного polling нет. UUID ресурса сохраняется в sessionStorage; потерянные команды автоматически не повторяются.

## Выполненные проверки

```sh
docker compose up --build -d --force-recreate --renew-anon-volumes
docker compose exec backend npm run check
docker compose exec frontend npm run check
docker compose -f compose.yaml -f compose.test.yaml run --build --rm e2e
docker compose exec backend node scripts/play-mock-match.mjs
docker compose exec -e API_BASE_URL=http://frontend:5173 backend node scripts/play-mock-match.mjs --errors
```

Backend: **80 тестов**, lint/typecheck/build пройдены. Три новых теста используют настоящее HTTP-соединение: начальный SSE snapshot, упорядоченные события, busy=false после OperationSettled, Reset/reconnect, Pause во время длинной межходовой задержки, shutdown с открытым потоком и снимок партии более 64 КБ.

Frontend: **6 тестов**, lint/typecheck/build пройдены. Проверены дедупликация и порядок событий, игнорирование старых снимков/игр после Reset, доступность команд, извлечение клеток только для аннотации, REST recovery и очистка EventSource, диагностика 404 до onopen после потери RAM-матча.

Chromium: **11 браузерных сценариев пройдены** через цепочку **браузер → Vite → backend**:

1. Доска с 64 клетками, автоматический матч, Pause/Resume/Next Move/Stop/Reset и навигация по истории.
2. IllegalMove/InvalidFormat: неизменная доска, подсветка a1, исходные ответы, категория/модель/диагностика, повтор и очистка журнала после Reset.
3. Пошаговый запуск и сценарный мат f3/e5/g4/Qh4#, SAN, режим B и исторический FEN, совпадающий с backend.
4. Reset при ожидающем Next Move: запрос отменён, спустя время ответа нет старого хода, ошибки или событий.
5. Offline/online: пропущенный ход и журнал восстанавливаются через REST; событие принято один раз; после восстановления REST polling отсутствует.
6. Исторический FEN остаётся выбранным при продолжающейся автоматической игре; возврат к актуальной позиции.
7. Reload вкладки восстанавливает тот же UUID/позицию/журнал без дубликатов.
8–11. Экраны 320/360/768/1440 px: 64 клетки, вертикальная/горизонтальная компоновка, отсутствие горизонтального переполнения и JS-исключений.

В обычном сценарии автоматического матча ошибок console.error/pageerror не зафиксировано. Сетевые ошибки намеренного offline и 404/409 при restart/отмене считаются ожидаемыми диагностическими ответами, а не ошибками выполнения React.

Дополнительно проверено в открытом Chromium:

- Временное изменение footer появилось через HMR без навигации страницы и без смены UUID матча. Проверочное изменение отменено.
- Изменение времени файла backend в bind mount вызвало nodemon restart: SIGTERM → Shutdown complete → восстановленный API. Открытый SSE не удерживал shutdown. Интерфейс сообщил об утрате RAM-матча; «Переподключить» создало новый матч и восстановило SSE. Необработанных JS-исключений не было.
- После пересоздания оба сервиса healthy; проверочный маркер в experiments сохранился. Постоянный volume не удалялся.
- Существующие HTTP-сценарии по-прежнему заканчиваются матом чёрных за 4 полухода и техническим поражением белых после двух IllegalMove без изменения доски.

## Ограничения и следующие этапы

- Только Mock Providers; настоящие API, ключи и inference runtimes не подключались.
- Матчи/попытки/события остаются в RAM. Backend restart удаляет их; сохранность самого volume не означает сохранность матчей. JSON Store, архив, освобождение старых ресурсов и файловый экспорт — этап 4. PGN доступен через snapshot.
- Применение настроек создаёт отдельный матч; Reset сохраняет настройки текущего ресурса. Режим автоматического/пошагового запуска — настройка интерфейса; Resume явно запускает автоматику.
- В UI нет заявления ничьей по 3 повторениям/50 ходам: оно доступно через REST. Правила автоматического завершения остаются на backend.
- Не проверялись Firefox/Safari, macOS и отдельная Linux host-система. Проверки размеров экрана не заменяют проверку на физических мобильных устройствах.
- SSE передаёт полные снимки, включая накопленные попытки. Оптимизация объёма больших экспериментов, виртуализация журнала и архивирование относятся к следующему этапу; нагрузочное тестирование верхних лимитов не проводилось.
