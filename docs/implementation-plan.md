# План реализации

**Этапы 1–3 завершены и проверены в Docker Desktop/WSL2 на Windows**, 15 ноября 2026 года. По заданию от 16 ноября интеграция произвольных Chat Completions API вынесена вперёд в этап 4A. Постоянное хранение и экспорт — этап 4B; специализированная инфраструктура runtimes — этап 5. Полные требования: [requirements.md](requirements.md), архитектура: [architecture.md](architecture.md), REST/SSE-контракт: [api.md](api.md).

## Этап 4A. Универсальный OpenAI-compatible Provider

- [x] HTTP Chat Completions без SDK поставщика: независимые Base URL/model ID/названия и server credential profiles.
- [x] Опциональные temperature, лимит и выбор max_tokens/max_completion_tokens, JSON mode без молчаливой смены параметров.
- [x] Проверка модели/параметров настоящим completion вручную и перед первым ходом; отдельные метрики preflight.
- [x] Общий и отдельные системные шаблоны, восстановление стандартного, подстановка color/FEN/ASCII/history при каждой попытке.
- [x] Строгий Parser/UCI/Chess Engine, feedback и бюджет retries, защита режима A и изоляция инструкций игроков.
- [x] Usage вход/выход/всего, время HTTP и попытки, неизвестные метрики null; учёт отклонённых ответов и исправленных повторов.
- [x] Тайм-аут чтения, AbortSignal, предел 1 MiB, 429/ошибки сети, запрет redirect и привязка ключа к точному URL.
- [x] Формы Mock/реальных API, параметры, профили, редакторы промптов, проверка доступности и ошибки.
- [x] HTTP-тесты на локальных Mock API, включая два разных endpoints; прежние тесты сохранены.
- [x] Контейнерная проверка: 96 backend, 6 frontend, 14 Chromium e2e; lint/typecheck/build, health/volume/HMR/restart. Отчёт [verification-stage-4a.md](verification-stage-4a.md).
- [ ] Условная проверка нескольких ходов двух настоящих LLM при доступных API и отдельном разрешении на платные запросы.

Реализация 4A проверена контейнерными тестами и игрой через тестовые совместимые HTTP endpoints. Проверка настоящих моделей не выполнена: server keys не настроены, локальные API на стандартных портах 11434/8000 недоступны; платные запросы не выполнялись. Эта условная проверка учитывается отдельно и не заменяется тестовым сервером. Хранение остаётся в RAM; vLLM CUDA на этом этапе не добавляется.

## Этап 4B. Постоянное хранение, экспорт и расширенная статистика

- [ ] JSON Store с атомарной записью, logger всех попыток, восстановление сохранённых результатов.
- [ ] Файловый экспорт PGN и полного JSON; сохранение завершённых, остановленных и сброшенных игр.
- [ ] Агрегировать статистику игроков из попыток; сохранять токены/метрики runtime по мере появления реального адаптера.
- [ ] Архив старых gameId, жизненный цикл/освобождение реестра и политика восстановления после рестарта backend.
- [ ] Тесты экспорта, ошибок хранения, секретов и shutdown во время записи.

Готово, когда сохранённые JSON согласованы с REST-снимком, эксперименты переживают пересоздание контейнеров, файлы экспортируются и не содержат секретов. На этапах 2–3 журнал и матчи находятся только в RAM, PGN доступен в snapshot; это не постоянное хранение.

## Этап 5. Специализированные локальные runtimes

- [x] Универсальный Chat Completions adapter и независимые настройки реализованы на этапе 4A.
- [ ] OpenAI/OpenRouter/Ollama, внешние vLLM CUDA/vLLM-Metal и Docker Model Runner.
- [ ] Необязательный profile nvidia: официальный образ с проверенной поддержкой Blackwell sm_120, GPU/cache/context/memory limits.
- [ ] Документация CUDA/Windows WSL2/macOS Apple Silicon, OOM-диагностика и ресурсные ограничения двух endpoints.
- [ ] Метаданные runtime/model revision/quantization/context, токены и время загрузки/генерации, когда доступны.
- [x] Панели настоящих моделей, проверка подключения и usage-метрики — этап 4A; специальные runtime-метрики остаются запланированными.

Готово, когда две реальные модели независимо подключаются и ходят; тесты протокола работают без реальных ключей, отсутствие GPU не мешает базовому запуску. Версии vLLM и GPU-совместимость подтверждены отдельно.
