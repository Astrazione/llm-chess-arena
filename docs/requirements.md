# LLM Chess Arena

Разработай полноценное локальное веб-приложение для проведения экспериментальных шахматных матчей между двумя большими языковыми моделями (LLM).

Приложение должно позволять подключать разные LLM через API, передавать им текущее состояние шахматной партии, получать выбранный ход, проверять его корректность и визуализировать процесс игры.

Основная цель проекта: исследование способности LLM понимать шахматные правила, выбирать ходы и поддерживать согласованное представление шахматной позиции.

Проект экспериментальный, поэтому приоритеты следующие:

1. Корректность шахматной логики.
2. Прозрачность взаимодействия с моделями.
3. Удобство управления экспериментом.
4. Простота и наглядность интерфейса.
5. Возможность воспроизводить и анализировать результаты.

## 1. Технологический стек

Используй:

- TypeScript для frontend и backend.
- React + Vite для frontend.
- Fastify для backend.
- chess.js для шахматной логики и проверки ходов.
- react-chessboard для визуализации шахматной доски.
- SSE для отправки событий матча в интерфейс.
- Локальное хранение партий и результатов в JSON.

Используй современные стабильные версии библиотек. Перед реализацией изучи их актуальные API.

Не используй тяжёлые архитектурные решения, если они не нужны для MVP.

## 2. Основная архитектура

Раздели приложение на независимые компоненты:

**Chess Engine**

Отвечает за состояние партии, легальность ходов, историю позиций, определение шаха, мата, пата, ничьей и других стандартных шахматных ситуаций.

**LLM Provider**

Абстракция для вызова языковых моделей. Реализуй адаптер для OpenAI-совместимых Chat Completions API с возможностью указать модель и базовый URL провайдера.

Предусмотри возможность подключения OpenAI, OpenRouter, Ollama и других совместимых провайдеров.

**Game Orchestrator**

Управляет матчем: выбирает модель, которая должна ходить, формирует запрос, получает ответ, проверяет ход и обновляет состояние партии.

**Experiment Logger**

Сохраняет ходы, попытки, ошибки, ответы моделей, временные характеристики и параметры эксперимента.

**Frontend**

Отображает доску, настройки, управление матчем, историю ходов, ошибки и статистику.

Сервер должен быть единственным источником достоверного состояния партии. Frontend только отображает состояние, полученное от сервера.

## 3. Настройка моделей

Пользователь должен иметь возможность независимо настроить две модели:

- Провайдер.
- Идентификатор модели.
- Роль в партии (белые или чёрные).
- Temperature, если параметр поддерживается.
- Лимит выходных токенов, если поддерживается.
- Тайм-аут запроса.

Разреши использовать одну и ту же модель для обоих игроков.

API-ключи должны храниться только на сервере, в переменных окружения. Не передавай их в браузер и не сохраняй в журнал экспериментов.

Предусмотри `.env.example`.

Если некоторые параметры не поддерживаются конкретным провайдером, приложение должно корректно обрабатывать эту ситуацию.

## 4. Формирование запросов к LLM

Каждая модель получает:

- Системную инструкцию с правилами участия в шахматной партии.
- Цвет фигур, которыми она играет.
- Текущую позицию в формате FEN.
- Текстовое представление доски (ASCII).
- Историю уже выполненных ходов.
- Требование вернуть следующий ход в определённом формате.

Используй UCI как основной формат ходов.

Примеры:

- e2e4
- g1f3
- e7e8q

Ожидаемый ответ модели:

```json
{
  "move": "e2e4"
}
```

Не запрашивай скрытые рассуждения модели. Для MVP достаточно самого хода.

Создай отдельный редактируемый шаблон системного промпта. Пользователь должен иметь возможность менять инструкцию перед началом партии.

Предусмотри два экспериментальных режима:

**Режим A: без подсказок**

Модель получает доску, FEN и историю ходов, но не получает список допустимых ходов.

**Режим B: с допустимыми ходами**

Дополнительно передаётся полный список легальных ходов в формате UCI.

Режим должен выбираться перед началом партии и сохраняться в результатах эксперимента.

Для обеих моделей используй одинаковые правила формирования контекста. Различаться должны только цвет фигур и состояние соответствующего игрока.

## 5. Игровой процесс

Реализуй следующий алгоритм:

1. Создать новую стандартную шахматную партию.
2. Определить активного игрока.
3. Сформировать запрос к соответствующей LLM.
4. Дождаться ответа модели.
5. Разобрать возвращённый ход.
6. Проверить его корректность через Chess Engine.
7. Если ход допустим, применить его.
8. Обновить доску, историю ходов и статистику.
9. Передать очередь хода второй модели.
10. Повторять до завершения или остановки партии.

Нельзя принимать ход только потому, что модель считает его допустимым.

Все изменения доски должны проходить через Chess Engine.

Корректно обрабатывай рокировку, взятие на проходе, превращение пешки, шах, мат, пат и ничейные окончания.

Предусмотри ограничение максимального количества полуходов для защиты от бесконечных экспериментов.

## 6. Обработка ошибок моделей

Ошибки являются важной частью эксперимента.

Выдели следующие категории:

- InvalidFormat: модель вернула ответ неправильного формата.
- IllegalMove: возвращённый ход невозможен по шахматным правилам.
- Timeout: модель не ответила за установленное время.
- ProviderError: ошибка при обращении к API.
- EmptyResponse: отсутствует содержательный ответ.

При недопустимом ходе:

1. Не изменяй состояние доски.
2. Зафиксируй ошибку и полный полученный ответ.
3. Покажи ошибку в интерфейсе.
4. Повтори запрос той же модели, сообщив причину отклонения предыдущего хода.
5. Если число попыток превышает установленный лимит, заверши партию техническим поражением этой модели.

Количество повторных попыток должно настраиваться.

Не исправляй и не заменяй ошибочные ходы автоматически.

Если предложенный недопустимый ход содержит корректные начальную и конечную клетки, можно подсветить их на доске, не перемещая фигуры.

Если ход нельзя интерпретировать, просто покажи текст ошибки рядом с шахматной доской.

Все ошибки должны попадать в журнал и статистику.

## 7. Управление матчем

Реализуй следующие действия:

**Start**

Создать новую партию с выбранными настройками и начать автоматическую игру.

**Pause**

Приостановить автоматическое выполнение новых ходов. Текущий запрос может завершиться, после чего новые запросы не запускаются.

**Resume**

Продолжить матч с текущей позиции.

**Next Move**

Выполнить ровно один ход активной модели, после чего остаться в состоянии паузы.

**Stop**

Завершить текущий эксперимент без определения победителя по шахматным правилам.

**Reset**

Сбросить состояние и начать новую партию.

Обязательно обработай конкурентные операции и асинхронные запросы. Запоздавшие ответы после Reset или Stop не должны изменять новую или завершённую партию.

Запрети параллельное выполнение нескольких ходов в рамках одной партии.

## 8. Интерфейс

Сделай минималистичный, современный и адаптивный интерфейс.

Основное расположение:

**Слева:**

- Шахматная доска.
- Названия моделей над и под доской.
- Подсветка последнего выполненного хода.
- Индикация активного игрока.
- Состояние партии.
- Кнопки управления.

**Справа:**

- Настройки двух моделей.
- Режим эксперимента.
- История ходов.
- Журнал событий и ошибок.
- Статистика партии.

Реализуй автоматическое обновление интерфейса после каждого хода.

Должна быть возможность просматривать предыдущие позиции партии, не изменяя её действительное состояние.

Для ошибок и запросов к API используй отдельные визуальные состояния.

Показывай, когда модель ожидает ответ сервера.

Предусмотри тёмную тему. Избегай перегруженного дизайна и лишних декоративных элементов.

## 9. Статистика и результаты

Для каждого игрока собирай:

- Количество успешно выполненных ходов.
- Количество недопустимых ходов.
- Количество ошибок формата.
- Количество повторных попыток.
- Среднее и суммарное время ответа.
- Использованные входные и выходные токены, если провайдер возвращает соответствующие данные.

Для всей партии сохраняй:

- Идентификатор эксперимента.
- Конфигурацию моделей.
- Использованные системные промпты.
- Режим эксперимента.
- Историю шахматных позиций и ходов.
- Все попытки моделей, включая отклонённые.
- Сырой текст ответов моделей.
- Временные метки.
- Результат партии и причину завершения.

Для журнала ошибок указывай модель, номер хода, тип ошибки, исходный ответ и диагностическое сообщение.

## 10. Экспорт

Реализуй экспорт:

**PGN**

Стандартная запись партии со всеми подтверждёнными легальными ходами.

**JSON**

Полный журнал эксперимента, включая настройки, запросы, ответы, ошибки, метрики и итоговые результаты.

Сохраняй завершённые и принудительно остановленные партии локально.

Не сохраняй API-ключи и другие секретные данные.

## 11. Тестирование

- Корректный ход модели.

## Контейнеризация и окружение разработки

Всё приложение должно разрабатываться и запускаться через Docker Compose с самого первого этапа.

Docker является основной средой выполнения проекта. Локальная установка Node.js, npm и других инструментов разработки на хостовую систему не должна быть обязательной.

### Требования

1. Создай отдельные Dockerfile для frontend и backend.
2. Создай `compose.yaml` в корне проекта.
3. Используй Docker Compose для запуска всех компонентов приложения.
4. Обеспечь возможность запуска проекта одной командой:

   `docker compose up --build`

5. Настрой автоматическое обновление приложения при изменении исходного кода без пересборки Docker-образов (hot reload).
6. Используй bind mounts для исходного кода в режиме разработки.
7. Обеспечь корректную работу на Windows с Docker Desktop и WSL2, а также на Linux.
8. Все зависимости должны устанавливаться внутри контейнеров. Исключи конфликты между локальными и контейнерными `node_modules`.
9. Настрой взаимодействие контейнеров через внутреннюю сеть Docker Compose.
10. Добавь health checks для backend и корректный порядок запуска зависимых сервисов.
11. Создай `.dockerignore` для каждого сервиса.
12. Используй переменные окружения и `.env.example` для конфигурации.
13. Не включай API-ключи и другие секреты в Docker-образы или исходный код.
14. Храни JSON-файлы экспериментов в постоянном Docker volume, чтобы они сохранялись после пересоздания контейнеров.
15. Предусмотри выполнение тестов и проверок сборки через Docker Compose.
16. Настрой graceful shutdown, чтобы остановка контейнера корректно завершала активные операции приложения.
17. По возможности используй многостадийные Dockerfile и запуск приложений от непривилегированного пользователя.

### Сервисы

**frontend**

- React + Vite.
- Порт разработки: 5173.
- Доступ из браузера через http://localhost:5173.
- Hot reload для React и TypeScript.
- Проксирование API и SSE-запросов на backend по имени сервиса Docker Compose.

**backend**

- Fastify + TypeScript.
- Порт: 3000.
- Прослушивание интерфейса `0.0.0.0` внутри контейнера.
- Поддержка hot reload.
- Доступ к API-ключам через переменные окружения.
- Хранение результатов экспериментов в постоянном volume.

Не добавляй отдельную базу данных, Redis, Kubernetes и другие инфраструктурные компоненты без необходимости.

### Проверка готовности

Первый этап считается завершённым только после успешного выполнения следующих условий:

- `docker compose up --build` запускает frontend и backend.
- Интерфейс открывается в браузере.
- Frontend может выполнять запросы к backend.
- Изменения в исходных файлах отражаются в работающем приложении без ручной пересборки.
- Контейнеры корректно останавливаются.
- Тесты запускаются внутри Docker.
- Данные в постоянном volume сохраняются после пересоздания контейнеров.

При разработке новых компонентов используй уже созданное Docker-окружение. Не переходи на локальный запуск сервисов вне Docker.


## Локальные LLM, vLLM и кроссплатформенность

Приложение должно поддерживать локальный GPU-инференс на следующих конфигурациях:

1. Windows 11 / Linux, NVIDIA RTX 5070 Ti, 16 GB VRAM.
2. macOS, Apple Silicon M5, около 25 GB unified memory.

### Требования к архитектуре

- Реализуй универсальный OpenAI-compatible LLM Provider.
- Не привязывай Game Orchestrator к конкретному движку инференса.
- Поддерживай vLLM CUDA, vLLM-Metal, Docker Model Runner, Ollama и облачные OpenAI-совместимые API.
- Для каждого шахматного игрока разреши независимо указывать provider, base URL, model ID и параметры генерации.
- Предусмотри проверку доступности модели перед началом партии.

### Docker

- Основной compose.yaml должен одинаково работать на Windows и macOS.
- Frontend и backend всегда запускаются через Docker Compose.
- NVIDIA vLLM реализуй как дополнительный сервис с Compose profile `nvidia`.
- Используй официальный образ vLLM, совместимый с CUDA и GPU Blackwell (sm_120). Проверяй совместимость выбранной версии.
- Настрой доступ к GPU, постоянное кеширование загруженных моделей и ограничения использования памяти.
- На macOS не пытайся передавать Metal GPU внутрь Linux-контейнера.
- Для macOS поддерживай подключение к vLLM-Metal или Docker Model Runner на хосте.
- Отсутствие GPU не должно препятствовать запуску основного приложения.

### Управление ресурсами

- Поддерживай запуск двух разных моделей.
- Учитывай ограничения памяти при одновременном использовании нескольких моделей.
- Не предполагай, что один экземпляр vLLM может одновременно обслуживать произвольные независимые модели без дополнительной конфигурации.
- Предусмотри возможность использования отдельных inference endpoints.
- Добавь настройки максимального контекста, количества генерируемых токенов и использования GPU-памяти.
- При нехватке памяти показывай диагностическую ошибку, не завершая основной backend.
- Разделяй время загрузки модели и время генерации ответа в статистике эксперимента, когда runtime позволяет это измерить.

### Экспериментальная воспроизводимость

В журнале партии сохраняй:

- Идентификатор и версию модели.
- Название inference runtime.
- Параметры генерации.
- Формат и параметры квантования, если известны.
- Максимальный контекст.
- Время ответа и количество токенов.
- Все попытки ходов, включая ошибочные.

Не объединяй статистику одинаковой модели с разными конфигурациями квантования без явного указания различий.

### Порядок реализации

На первом этапе создай архитектуру провайдеров и рабочее Docker-окружение.

На этапе интеграции с LLM добавь поддержку vLLM CUDA и внешних OpenAI-совместимых серверов, включая vLLM-Metal.

Не делай наличие запущенного vLLM обязательным условием запуска приложения.

Добавь в README отдельные инструкции для NVIDIA CUDA, Windows WSL2 и macOS Apple Silicon.
