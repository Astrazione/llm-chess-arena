# Правила разработки LLM Chess Arena

## Обязательная среда

- Разработка, запуск, установка зависимостей, тесты, линтеры и компиляция выполняются **только в Docker через Docker Compose**. Node.js/npm на хосте не требуются. Не обходить недоступный Docker локальным запуском.
- Основной запуск: `docker compose up --build`. Проверки: `docker compose exec backend npm run check` и `docker compose exec frontend npm run check`.
- Браузерные тесты: `docker compose -f compose.yaml -f compose.test.yaml run --build --rm e2e`.
- Исходники доступны через bind mounts; `node_modules` и `dist` изолированы в анонимных volumes. Не создавать host node_modules.
- После изменения зависимостей обновить соответствующий package-lock.json внутри контейнера и выполнить `docker compose up --build -d --force-recreate --renew-anon-volumes`. Постоянный volume experiments сохранять.
- Не выполнять `docker compose down --volumes` без явного запроса пользователя на удаление экспериментов.
- Если Docker не работает, честно отметить непроведённые проверки и оставить этап незавершённым.

## Архитектура

- Сначала читать `docs/requirements.md`, `docs/architecture.md`, `docs/implementation-plan.md`. Реализовывать текущий этап; не расширять его шахматной логикой или LLM-интеграцией заранее.
- Backend — единственный источник состояния партии; frontend отображает снимки и SSE-события.
- Слои backend: HTTP → прикладные сценарии/оркестратор → домен и порты; адаптеры chess.js, OpenAI-compatible и JSON storage подключаются через композицию зависимостей. Домен не импортирует Fastify/React.
- Оркестратор зависит от LlmProvider, а не от OpenAI/vLLM/Ollama. Каждый игрок имеет свою конфигурацию и endpoint. Проверять доступность и поддерживаемые параметры до матча.
- Все изменения доски проходят через Chess Engine. Не исправлять неверные ответы LLM автоматически и не запрашивать скрытые рассуждения.
- На одну партию — максимум один активный ход; AbortSignal и версия запуска защищают от запоздавших ответов после Stop/Reset. Документировать семантику Pause и Next Move.
- Хранение JSON — только в DATA_DIR (volume). В дальнейшем писать атомарно через временный файл и rename; сохранять все попытки, параметры и метаданные воспроизводимости.
- Не добавлять БД, Redis, очереди, обязательный inference-сервис или другие инфраструктурные компоненты без обоснованной потребности.

## Соглашения

- TypeScript strict, ESM; backend использует `.js` в относительных импортах исходного TypeScript (NodeNext). Осмысленные интерфейсы без пустых реализаций и ненужных фабрик.
- Входные HTTP-данные проверять схемами, ответы определять явно; будущие события и JSON-файлы версионировать.
- API-ключи — только server env. Не передавать секреты в VITE_*, HTTP-ответы, SSE, промпты и журналы; не логировать process.env или весь provider config.
- Сохранять Fastify app factory отдельно от listen; при SIGINT/SIGTERM закрывать сервер и активные операции через lifecycle hooks.
- Backend слушает 0.0.0.0. Браузер использует относительные `/api/*`; Vite проксирует REST/SSE на `backend:3000`. Для dev-сервисов сохранять привязку host-портов к 127.0.0.1.
- Добавлять содержательные тесты критического поведения. Использовать Mock Provider вместо реальных ключей в автоматических тестах.
- Проверять lint, typecheck, test и build обоих сервисов после изменений. Для изменений сетевого взаимодействия проверять реальную цепочку браузер → Vite → backend.
- После пересоздания проверять health checks и сохранность volume. Для hot reload проверять frontend HMR и backend restart с последующим восстановлением API.
- Обновлять README, план и результаты проверки; отличать выполненное от запланированного. Документация проекта — на русском.
